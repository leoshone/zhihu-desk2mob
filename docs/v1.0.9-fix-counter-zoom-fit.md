# v1.0.9 · 反缩放改为「恰好铺满」，消除打开页面时的那一点点放大

## 1. 现象

打开知乎页面后，页面比屏幕**宽一点点**（像被双指放大了一点点），
必须双指捏合缩回去，才能回到正常大小。每次打开都要捏一次。

## 2. 定量：差 9.9%

真机实测两个宽度：

| 量 | 实测值 |
| --- | --- |
| 屏幕可用 CSS 宽度 | **357.5**（1080 ÷ dpr 3.0235） |
| 脚本用的列宽 `SW` | **393**（取自 `screen.width`） |
| 比值 | **393 / 357.5 = 1.0992** |

老公式是 `html{zoom} = 1 / 浏览器缩放比例`，它保证的是「正好铺满 393 宽的屏幕」；
而实际屏幕只有 357.5 宽 —— 于是内容恒**大 9.9%**。

判据：内容在布局坐标下的宽度 ÷ 可见宽度（`fitRatio`）。`=1` 才是恰好铺满。
老公式在整个生命周期里恒为 **1.0992**。

## 3. 为什么时好时坏、难复现

浏览器在加载期会**逐级**调整缩放，而级差恰好也是 ×0.9097（= dpr 比例）。
于是老代码「上一级算出的 `1/scale`」常常正好等于「这一级铺满所需的值」——
看起来是对的；只有等到它用**当前**比例算一次，才会露出那 10%。

真机采样（每 220ms，加载全程）：

```
老版本：fitRatio [1.0001, 1.0001, 1.0992, 1.0992, …]   ← 前 0.45s 对，之后一直卡在 1.0992
        visual   [0.9099, 0.9099, 1.0000, 1.0000, …]   ← 视觉尺寸从 0.9099 跳到 1.0 并停住
新版本：fitRatio [1, 1, 1, …]（22/22）
        visual   [0.9098 × 22]                          ← 全程恒定，抖动 0%
```

## 4. 修法：让 zoom 瞄准「铺满」，而不是瞄准 `1/scale`

```js
const visW = vv ? vv.width : window.innerWidth;   // 可见范围内的布局 px
const Z = visW / SW;                              // ← 恰好铺满，而不是 1 / scale
```

这个改法还有一个关键性质，正好满足「不要有放大再缩小的视觉跳变」：

```
屏幕上的实际尺寸 = SW × Z × scale × dpr
                 = SW × (visW / SW) × scale × dpr
                 = visW × scale × dpr
                 = 屏幕宽度          ← 恒定，与 scale / visW 怎么变都无关
```

所以加载期间布局视口一路变化（实测 980 → 1077 → 1184 → 1301）、脚本反复重算 Z，
**视觉上完全不会有变化** —— 这是数学保证，不是"通常不会"。

## 5. 用户捏合仍然有效

只监听 `window.resize` 不够（浏览器改比例时不触发它，会留下过期 zoom）；
但直接监听 `visualViewport.resize` 又会在用户捏合时把页面拉回、让人捏不动。

区分办法：**看「屏幕可用宽度」有没有变**。
用户捏合会同时改变 `scale` 与 `visualViewport.width`，而两者乘积（= 屏幕可用宽度）不变
（实测：scale 1 → width 358；scale 0.5 → width 715，乘积都是 357.5）；
浏览器自己调整 dpr / 视口时该乘积才会变。因此：

```js
window.visualViewport.addEventListener('resize', () => {
  const vv = window.visualViewport;
  if (Math.abs(Math.round(vv.width * vv.scale) - curScreenW) <= 2) return;  // 只是捏合 → 不干预
  applyZoom();
});
```
