# v1.1.0 · 限制「手工缩小」：内容不会被缩到小于「恰好铺满」

## 1. 现象

在**专栏页**双指捏合可以一直缩到很小（实测最小只占屏宽 **49%**，半屏小字）。
用户要求「限制手工缩到很小」，并希望与首页/问答页表现一致。

## 2. 定量（真机实测）

| 量 | 值 |
| --- | --- |
| 布局视口 `innerWidth` | 891 |
| 屏幕可用 CSS 宽 | 358（= `vvWidth × scale`，**捏合不变量**）|
| 浏览器允许的捏合下限 | `scale = 0.40111`（= 358 / 891，再小被夹住）|
| 缩到下限时 `html{zoom}` | 未变（1.11786 或 0.90976，取决于此前状态）|
| 缩到下限时的视觉尺寸 | `visualSize ≈ 0.45`，只有铺满值 **0.910** 的一半 |

**关键否证**：逐档扫 `Emulation.setPageScaleFactor`（1 → 0.8 → 0.6 → 0.5 → 0.45 → 0.4 → 0.35 → 0.3 → 0.25），
专栏页与问答页读数**逐档一致**，都被夹在 0.40111。
所以「问答页限制得住、专栏页限制不住」**不是浏览器行为差异**。

真正的差异是**脚本有没有在捏合后重新铺满**：问答页某次把 `zoom` 重算成 2.26808（= 891 / 393），
专栏页没重算 —— 同一个手势，两页表现不同。**这一点是不稳定的**，同一页不同时刻都可能不一样。

## 3. 根因：两条 resize 路径的守卫不一致

| 路径 | 守卫 | 捏合时的行为 |
| --- | --- | --- |
| `window.resize` → `applyZoom` | 无 | **重算**（内容被拉回铺满，用户感觉「缩不下去」）|
| `visualViewport.resize` → 老代码 | 「屏幕可用宽度没变就 return」 | **不重算**（内容真的变小了）|

捏合恰好不改「屏幕可用宽度」这个乘积，所以 `visualViewport` 那条路一律忽略捏合；
而 `window.resize` 是否触发取决于浏览器，于是**谁先到就决定结果** → 时灵时不灵。

## 4. 修法：按方向分开处理

判据是**铺满时的视觉尺寸**（把 `Z = visW / SW` 代进 `Z × scale` 即得，**与 scale 无关**）：

```
fillVisual = curScreenW / SW          // = 屏幕可用宽 / 列宽
当前视觉尺寸 = html{zoom} × scale
```

| 情形 | 行为 |
| --- | --- |
| 当前视觉尺寸 **<** fillVisual（捏合缩小缩过头）| 拉回铺满 |
| 屏幕可用宽度变了（浏览器改 dpr/视口）| 重算 |
| 其余（捏合**放大**）| 不干预 |

```js
if (window.visualViewport) window.visualViewport.addEventListener('resize', () => {
  const vv = window.visualViewport;
  const fillVisual = curScreenW / SW;                       // 「恰好铺满」时的视觉尺寸
  const zNow = parseFloat(document.documentElement.style.zoom) || 1;
  if (CFG.limitZoomOut && curScreenW > 0 && zNow * vv.scale < fillVisual - 0.02) { applyZoom(); return; }
  if (Math.abs(Math.round(vv.width * vv.scale) - curScreenW) <= 2) return;
  applyZoom();
});
```

容差取 0.02：`curScreenW` 是取整过的，太小会自己误触发；而 2% 的缩小肉眼看不出来，
不影响「限制缩到很小」这个目标。

### 4.1 「拉回铺满」必须**延后一拍**再算（同版内修）

就地重算有一个**顺序敏感**的 bug。浏览器换挡时会先经过一个中间态 —— 实测
`Emulation.setPageScaleFactor(0.5)` 会**先来一发** `visW = innerWidth`（极小比例）的
`visualViewport.resize`。就地重算会按这个中间态算出过大的 zoom（`891 / 393 = 2.268`）；
紧接着真正那一发 `(715, 0.5)` 到来时，`zoom × scale = 1.134` 已经**大于**铺满值 0.9109
→ 被判定成「用户放大」而不纠正；乘积检查又是 `358 vs 358`（捏合不变量）→ 直接 return。
结果停在 `fitRatio = 1.2465`：**内容比屏幕宽 25%、右侧被裁**。

```js
let zoomFixTimer = null;
function refitSoon() { clearTimeout(zoomFixTimer); zoomFixTimer = setTimeout(applyZoom, 200); }
// 判定「缩过头」时改为 refitSoon()，不再就地 applyZoom()
```

延后 200ms 时比例已稳定，按**最终**几何重算才对；而且**放大方向不受影响**
（放大本来就不走这个分支），所以「捏合放大仍然有效」这条断言照样通过。
`__z2mStop()` 里一并清掉这个定时器。

> 教训：这类「按当前几何反推目标值」的规则，不要在事件回调里就地生效 ——
> 事件可能来自过渡态。**等布局稳定再校正**。

## 5. 验证（真机，Kiwi + 暴力猴实装 1.1.0）

| 动作 | 修前 | 修后 |
| --- | --- | --- |
| 捏合到 `scale 0.5` | `zoom` 不变，`visualSize` 0.45488（半屏小字）| `zoom` → **1.81952**（= 715/393），`visualSize` **0.90976** = 铺满 |
| 捏合到浏览器下限 `0.40111` | `visualSize` ≈ 0.45 | 仍停在 0.90976 |
| 捏合**放大** | 不变 | 不变（不干预，字还能放大）|

> 顺带说明「夹住的是下限」而不是「一律抢回」：放大过的页面再捏合缩小时，会一路缩到铺满才停，
> 不会被困在放大态。

`scripts/test-counterzoom.js`（`--installed`）的断言已随之改写：
① 加载全程恰好铺满且不跳变；② 捏合缩小后仍恰好铺满、屏幕实际尺寸不变；③ 缩到浏览器下限仍停在铺满；
④ 捏合放大不被抢回。

**全套真机回归（6 套，共 65 条断言）全绿**：

| 套 | 结果 |
| --- | --- |
| `test-counterzoom --installed` | 7/7 |
| `test-idea-option --installed` | 8/8 |
| `test-avatar --installed` | 8/8 |
| `test-rightrail --installed` | 9/9 |
| `test-comment-back --installed` | 23/23 |
| `test-modal-layout`（受控夹具）| 10/10 |

> 跑之前先确认**设备上开着专栏页与回答页各一个标签**：`test-idea-option` 优先用专栏页、
> 弹层类测试需要回答页。缺了它们测试会退到别的页面，表现成「发布框打不开」这类前置失败
> —— 那是环境问题，不是产品回归。
>
> ⚠️ **本表是「跑通过」的记录，不是稳定结论**：`test-counterzoom` 的 ②③ 会**间歇**失败
> （同一份代码两次运行可能 5/7 或 7/7）。机理与两次无效的修法见

## 6. 与 v1.0.9 的关系（重要）

v1.0.9 §5 明确写「用户捏合仍然有效、脚本不干预」。**v1.1.0 只推翻其中「缩小」这一半**，
放大仍然不干预 —— 因为「能缩到半屏小字」是用户明确不要的。
若日后要恢复「捏合一律自由」，把 `CFG.limitZoomOut` 置为 `false` 即可，不必回滚代码。
