# v1.1.1 · 正文按真机手感微调：屏上换算因子 0.98

## 1. 需求与「怎么定出 0.98」

用户反馈正文偏小。先做过一版把因子设成 **1.1**（屏上 17.6px），用户觉得**太大**、要求回退；
随后用户**自己在真机上手捏合**到合适大小，要求「参考我打开的页面」定值。

**定值方法（可复用）**：写探针逐个标签量出「屏上换算因子」（`zoom × scale`）与正文字的屏上 px，
找出用户捏过的那一个：

| 标签 | `zoom` | `scale` | 屏上因子（= 期望的 `textScale`）|
| --- | --- | --- | --- |
| 专栏文章 `p/1986764167131206949` | 2.26808 | 0.43208 | **0.97998** ← 用户捏的 |
| 首页（另一个标签，较早的捏合）| 2.26808 | 0.41476 | 0.94071 |

取 **`CFG.textScale = 0.98`**。三档对照：

| 版本 | 屏上正文字号 |
| --- | --- |
| 原默认（因子 0.90976）| 14.56px（嫌小）|
| **本版（0.98）** | **15.67px** |
| 已回退的 1.1 | 17.6px（嫌大）|

## 2. 机制（与已回退的 1.1 相同）

单列布局里 **屏上大小 = 名义字号 × (屏幕可用宽 ÷ 列宽)**，唯一的旋钮是**列宽**：

```
列宽收窄 → zoom = visW / 列宽 同比变大 → 屏上变大
列宽 × zoom × scale 恒等于屏幕可用宽 → 列依旧恰好铺满，右侧不裁
```

**不动任何 `font-size`。** 列宽用「实际可用宽」反推（而不是 `screen.width`），
于是屏上因子恒等于 `CFG.textScale`。真机：列宽 393 → 365，`fitRatio` 仍 = 1。

## 3. 已知未修：`test-counterzoom` 的 ②③ 会**间歇性**失败（与本次改动无关）

```
FAIL  捏合缩小后内容仍恰好铺满        -> {"fitRatio":1.2465,"scale":0.5}
FAIL  捏合缩小不改变屏幕上的实际尺寸    -> {"before":0.9795,"after":1.221}
```

**机理（已定位）**：`Emulation.setPageScaleFactor(0.5)` 会**先经过「最小比例」那一档**
（`visW == innerWidth`）。按那一档重算出的 zoom 过大（`891 / 365 = 2.441`）；紧接着真正那一发
`(715, 0.5)` 到来时，`zoom × scale = 1.22` 已经**大于**铺满值 0.9795 → 被判定成「用户放大」而不纠正；
而乘积检查（`715 × 0.5 = 358` vs `curScreenW 358`）又因为捏合不变量而成立 → **直接 return**，
最后那一发事件就这样被吞掉。

**这是 v1.1.0 就有的问题**，不是本版引入的：已发布的 v1.1.0 同样会间歇失败，也曾在另一次运行里 7/7 全过。

**试过并已回退的两种改法**（都无效，故代码保持最简）：

1. 只把「拉回铺满」**延后 200ms**；
2. 延后 + 若重算时仍停在最小比例就**再等一拍**（最多 3 次）。

两者都消不掉它，因为真正的缺口是「最后那一发事件因乘积不变而被 return」。

**为什么不再猜着改**：要根治必须能区分「用户主动放大」与「浏览器换挡的中间态」，
而两者**可观测状态完全相同**（`zoom × scale` 都大于铺满值、乘积都不变），
除非引入手势级信号（可行性未验证）。另外这个中间态在真机上是否会出现**尚未证实**
（它由 CDP 的 `Emulation.setPageScaleFactor` 触发；真实捏合是连续的），
且即便出现，用户**再捏一下即可恢复**。

## 4. 副作用

列变窄会让**固定尺寸的 UI 行**变挤（头像、按钮仍是原来的 CSS 尺寸）。已补一处：

```css
.AuthorInfo { text-overflow: ellipsis !important; }   /* 长作者名不再被硬切 */
```
