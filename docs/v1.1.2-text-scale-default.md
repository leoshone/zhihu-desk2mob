# v1.1.2 · 默认文字大小回到名义字号：屏上换算因子 0.98 → 1.0

## 1. 需求与定值

用户已在真机上**手动**把 `CFG.textScale` 改成 `1.0` 并实际用了一段时间，确认满意，
于是要求把它写成默认值 —— 免得换机、清数据或新装的人还要自己手改一次。

与 v1.1.1 的定值方式不同，请注意区别：

- `0.98` 是**捏合量出来的**（用户手动捏到 `zoom × scale = 0.97998` 作为基准）。
- `1.0` 是**取整到「名义字号」**，**不来自捏合** —— 属于有意偏离那次实测。

三档对照（本机屏幕可用宽 = 358 CSS px）：

| 版本 | `textScale` | 列宽（= 可用宽 ÷ 因子）| 正文屏上字号 | 每行汉字（≈ 列宽 ÷ 16）|
| --- | --- | --- | --- | --- |
| v1.0.9（铺满原始大小）| 0.90976 | 393 | 14.56px | ≈ 24 字 |
| v1.1.1（按捏合定值）| 0.98 | 365 | 15.67px | ≈ 22 字 |
| **v1.1.2（本版）** | **1.0** | **358** | **16.0px（= 名义字号）** | **≈ 22 字** |

> 1.0 仍**小于**此前被否掉的 `1.1`（屏上 17.6px，用户觉得太大），所以它是「比 0.98 略大、
> 但没到大到被否」的一档。

## 2. 机制（未变）

单列布局里**屏上大小 = 名义字号 × (屏幕可用宽 ÷ 列宽)**，唯一的旋钮是**列宽**：

```
列宽 = 屏幕可用宽 ÷ CFG.textScale
zoom = 可见宽度 ÷ 列宽        →   zoom × scale 恒等于「铺满」
```

于是**屏上换算因子恒等于 `CFG.textScale`**，且**不动任何 `font-size`**；列依旧恰好铺满
（`fitRatio = 1`），右侧不会被裁。实现与 v1.1.1 完全相同，本版只改了那一个数。

一个容易误判的细节（**排查时先看这里**）：当浏览器自身的 `scale` 已经是 1（内容本就铺满）时，
`Z = visW / SW = 358 / 358 = 1`，**恰好等于 `curZ` 的初值 1**，于是 `applyZoom()` 里

```js
if (Math.abs(Z - curZ) < 0.005) return;   // Z === curZ === 1 → 直接 return
```

会**提前返回、不写内联 `style.zoom`**。这是**正确行为**（没有需要调整的东西），
但它会让 `test-counterzoom` 的①步拿不到样本（该步只统计「有内联 zoom」的采样）——
见 §4 的工装缺陷。

## 3. 副作用

- **列宽 365 → 358**（窄 7px，约 1.9%）：每行汉字数四舍五入后与 0.98 同档（≈ 22 字），
  页面长度几乎不变；固定尺寸的 UI（头像、按钮）相对再挤一点点，但实测各套回归均无异常。
- **正文屏上 15.67px → 16.0px**（+2.1%），这正是本次的目的。

## 4. 验证（真机 Kiwi + 暴力猴，实装 1.1.2）

| 套 | 结果 |
| --- | --- |
| `test-comment-back --installed` | 23 / 23 |
| `test-idea-option --installed` | 8 / 8 |
| `test-avatar --installed` | 8 / 8 |
| `test-rightrail --installed` | 9 / 9 |
| `test-modal-layout`（受控夹具）| 10 / 10 |
| `test-counterzoom --installed` | **5 / 7** —— ②③ 失败，见下 |

**②③ 的失败是既有问题，本版未引入**。A/B 已对照：把 v1.1.1 的发布件装回真机跑同一测试，
**结果同样是 5 / 7**，且失败数值与 `v1.1.1-text-scale.md` §3 记录的**逐字一致**：

```
FAIL  捏合缩小后内容仍恰好铺满            -> {"fitRatio":1.2465,"scale":0.5}
FAIL  捏合缩小不改变屏幕上的实际尺寸      -> {"before":0.9795,"after":1.221}
```

（在 1.1.2 上是 `before 0.9987 → after 1.2449` —— 同样的形态，只差 textScale 带来的基线。）
机理与两次无效的修法见 [`v1.1.1-text-scale.md`](v1.1.1-text-scale.md) §3；真机连续捏合不经过
那个由 `Emulation.setPageScaleFactor` 造出的中间态。

### 本次新发现的一处工装缺陷（已同步进技能）

`test-counterzoom` 的 ②③④ 会 `Emulation.setPageScaleFactor`，收尾只 `Page.navigate` **不还原**，
于是**被它选中的那张标签会残留 `scale = 1`**。而它每次都取**第一个**匹配 `www.zhihu.com` 的标签
⇒ 紧接着重跑时，①步必然拿到 **0 个样本**（表现为 3 条 FAIL，看起来像 renderer 挂死，其实不是）。

对策：重跑前把那张残留标签移出匹配范围（或重启 Kiwi）。此前 SKILL.md 把「0 采样」只归因于
**后台标签被冻结**，本次补齐了这个更容易踩的成因。
